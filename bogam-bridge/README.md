# 동의보감 수동 새로고침 연동

Desk의 **오늘 n/m명 → 하단 동의보감 새로고침**에서 진료·접수 기간과 예약 기간을 각각 지정합니다. 각 기간은 최대 366일입니다. 처음에는 오늘 하루이며, 같은 브라우저에서 마지막으로 선택한 기간을 기억합니다. 버튼 클릭만 조회를 시작합니다. 시간·요일 제한, 정기 조회, 자동 재조회, 재시도, 서비스 등록, 예약 작업은 없습니다. 화면을 열거나 서버를 재시작하거나 상태를 읽는 것만으로 동의보감 DB를 조회하지 않습니다.

## 구조와 데이터 범위

브라우저 → 기존 진료보드 인증 → 진료보드 서버 → HTTPS + 공유 토큰 → 데스크 PC의 Node 연동 프로그램 → **공유 메모리 `lpc:.\SQLEXPRESS`, Windows 인증, BogamDB**.

SQL Server TCP 포트나 SQL Browser 포트는 개방하지 않습니다. 데스크 PC의 연동 프로그램 HTTPS 포트(기본 8788)만 진료보드 서버 IP에서 접근하도록 제한합니다. 브라우저에는 토큰이나 SQL 연결 정보를 보내지 않습니다. 브리지도 요청의 원본 IP와 토큰을 둘 다 확인합니다. TLS 인증서 검증은 끄지 않습니다.

확인된 매핑만 사용합니다.

| 목적 | 원본 |
| --- | --- |
| 진료·접수 | `dbo.DigMast`와 `dbo.DigAccept`: 진료번호 + 고객번호 + 진료/접수 날짜로 LEFT JOIN |
| 진료 필드 | `dm_DiagID`, `dm_CustID`, `dm_DiagDate`, `dm_DiagTime`, `dm_DrEmp` |
| 접수 필드 | `da_DiagID`, `da_CustID`, `da_AccDate`, `da_AccTime` |
| 예약 | `dbo.DigBook`: `dbk_CustID`, `dbk_DiagDate`, `dbk_DiagTime`, `dbk_DrEmp` |
| 고객 | `dbo.CustMast.cm_CustID` → `cm_ChartID`, `cm_CustName` |
| 의사명 | `dm_DrEmp` / `dbk_DrEmp` → `Employe.emp_Code` → `emp_Name` (진료 52/52, 예약 39/39 일치 보고) |

예약 조회 기간은 **방문 예정일 `dbk_DiagDate`** 기준입니다. 예약을 등록한 `dbk_BookDate/Time`을 방문 시각으로 사용하지 않습니다. `TreatRoom`, `TreatRoomHist`는 조회하지 않습니다. 검증된 금액과 주상병코드를 가져옵니다. 주상병명은 아래 유효 기간·이름 유일성 조건을 만족할 때만 갱신합니다. 치료 종류·예약 메모는 가져오지 않습니다. 고객코드가 차트번호라고 가정하지 않습니다.

### 기존 엑셀 로직과 병합 정책

- 진료·접수 수동 엑셀: 차트번호를 정규화하고 이름과 함께 환자를 찾으며, `visitHistory[날짜]`에 병합합니다. 직접 연동도 같은 환자 식별, 서버의 `mergePatientImportRecord(..., true)`와 `savePatient`/진료 인덱스를 재사용합니다. 직접 조회 원본은 `bogamVisitRecords`에 진료번호+고객번호+날짜별로 별도 저장합니다. 같은 날 여러 진료번호가 있으면 일별 요약을 새로 만들거나 합산하지 않고 기존 값을 유지합니다. 퇴실이나 치료실 입실 시각을 접수 시각으로 사용하지 않습니다.
- 진료·접수 자료에서 차트번호가 같은 다른 이름과 충돌하면 엑셀과 같이 해당 차트번호의 환자만 저장 보류하고 나머지를 반영합니다. 한 조회 안에 같은 차트번호의 서로 다른 이름이 있으면 해당 차트번호의 모든 진료를 사전 제외합니다. 완료 상태에는 제외 환자 수와 진료 건수만 표시하며 로그에 식별값을 남기지 않습니다. 직접 조회는 진료번호+고객번호+날짜를 기준으로 재수신을 병합하여 같은 진료번호를 중복 추가하지 않습니다. 기존 날짜별 방문 목록도 중복 날짜를 만들지 않습니다. 기존 기록의 치료 목록, 부위, `memo2`, 메모 이력, 패키지, 수기 보정 등을 보존합니다. 진료비는 아래 검증 범위와 조건에 한해 갱신합니다. 이 연동은 접수→대기실 등록이나 치료 완료/퇴실 처리를 자동 실행하지 않습니다.
- 예약 수동 엑셀과 직접 연동 모두 **결과에 포함된 날짜의 전체 명단 교체**입니다. 같은 검증·암호화 저장·복구 이력 코드를 공유합니다. 슬롯은 차트번호+이름+시간+의사명으로, 환자 수는 차트번호+이름으로 중복 제거합니다. 포함된 날짜의 기존 슬롯 중 이번 명단에 없는 것은 제거되며 수동 예약도 새 명단에 없으면 제외됩니다.
- **엑셀 방식으로 변경해달라는 사용자의 후속 요청에 따라** 예약 추가 병합을 전체 명단 교체로 변경했습니다. 결과에 없는 날짜는 유지합니다. 예약이 0명인 날짜는 기존 예약 불러오기 팝업의 명단 비우기로 명시적으로 처리합니다. 이 동작은 dbk_Accept의 의미나 예약 ID 안정성을 확인한 것으로 간주하지 않으며, 날짜 이동을 ID로 자동 연결하지 않습니다.
- 진료보드의 환자·예약·마지막 성공 시각은 하나의 로컬 SQLite 트랜잭션에 저장합니다. 어느 단계라도 실패하면 전부 롤백합니다. 예약 이전 명단은 기존 암호화 가져오기 이력에 보관됩니다. 기존 수동 가져오기 버튼과 동작은 유지합니다.
- 여러 브라우저가 같은 기간으로 동시에 누르면 서버의 진행 중인 하나의 작업을 공유합니다. 다른 기간이면 `SYNC_BUSY`를 반환합니다. 브리지도 실제 SQL 프로세스가 종료될 때까지 단일 잠금을 유지합니다.

## 1. 데스크 PC 설치 (아직 DB 조회 안 함)

1. Windows에 Node.js 22.13 이상 LTS를 설치합니다. 개발 PC에서 생성한 `bogam-bridge.zip`을 데스크 PC의 로컬 폴더(예: `C:\inhouse-bogam`)에 풉니다. OneDrive 경로에 비밀 파일을 두지 않습니다. 별도 npm 패키지는 필요 없습니다. Windows PowerShell 5.1과 .NET의 SqlClient를 사용합니다.
2. **현재 Windows 계정이 SQL 관리자인지 먼저 인지**하세요. 처음 접속에 사용했던 SQL 관리자 계정으로는 아래 검증 모드만 사용할 수 있습니다. 실제 반영은 기존 조회 전용 계정으로 실행하고 권한 검사에 통과해야 합니다. DB 계정·권한을 만들거나 변경하는 명령은 포함되어 있지 않습니다.
3. 데스크 IP와 진료보드 서버 IP를 고정/예약한 뒤 다음을 실행합니다. 이 스크립트는 로컬 사용자 TLS 인증서와 외부 비밀 폴더만 만들며 DB에 접속하거나 방화벽을 변경하지 않습니다. 기존 폴더를 덮어쓰지 않습니다.

```powershell
cd C:\inhouse-bogam
.\bogam-bridge\initialize-secrets.ps1 -DeskIp 192.168.0.20 -ServerIp 192.168.0.10
$env:BOGAM_BRIDGE_CONFIG = "$env:LOCALAPPDATA\InhouseBogamBridge\bridge.json"
```

4. 해당 폴더는 생성한 Windows 사용자만 접근할 수 있습니다. 실제 실행할 **기존** Windows 계정에서 비밀 폴더를 준비하세요. 다른 계정의 자격 증명을 설정 파일에 저장하지 않습니다. 토큰/PFX/암호를 채팅·이슈·Git·환자 로그로 공유하지 마세요. 인증서는 1년 후 만료하므로 만료 전에 별도의 새 폴더에 재발급하고 서버의 신뢰 인증서도 교체합니다.

## 2. 기존 계정·형식 확인 (SELECT 메타데이터만)

```powershell
node .\bogam-bridge\bridge.js --inspect
```

이 명령은 현재 계정의 `readOnlyVerified`, 확인된 관련 테이블의 열 이름/자료형, 현재 권한에서 볼 수 있는 기존 DB 사용자/역할을 출력합니다. 환자 데이터는 출력하지 않습니다. `sys.fn_my_permissions`와 역할 정보에 대한 SELECT만 사용합니다. 보이는 사용자 목록이 SQL 로그인 가능 여부나 그 계정의 실제 유효 권한을 증명하지는 않습니다. **기존 계정으로 실제 로그인해서 동일 명령을 다시 실행해야 합니다.** SQL 전용 로그인의 암호를 이용하는 경로는 구현하지 않았으며, 기존 Windows 사용자/그룹으로 접속해야 합니다.

`readOnlyVerified`는 sysadmin/db_owner/db_datawriter 및 서버·DB·스키마·개체의 비조회 권한이 없음을 보수적으로 검사한 결과입니다. 쓰기·실행·권한 부여 능력이 있거나 확인할 수 없으면 실제 반영을 거절합니다. `ApplicationIntent=ReadOnly`를 접근 통제로 오인하지 않습니다. 기존 조회 전용 계정을 사용할 수 없으면 관리자 계정으로 반영을 강행하지 말고 검증 모드에 둡니다. 계정 변경은 이 작업 범위에 포함되지 않습니다.

`bridge.json`에서 다음을 확인 후 설정합니다.

```json
{
  "mappingVerified": true,
  "dateStorage": "yyyymmdd",
  "applyEnabled": false
}
```

- `dateStorage`: 날짜 열이 `YYYYMMDD` 형식 char/varchar이면 `yyyymmdd`, SQL date/datetime이면 `date`입니다. 관련 날짜 열 모두 동일하게 비교 가능한 형식인지 먼저 확인합니다. 형식이 다르면 추측하지 말고 어댑터를 보완해야 합니다. 범위 조건은 원본 날짜 열에 함수나 CAST를 씌우지 않고 자료형에 맞는 매개변수로 비교합니다.
- `mappingVerified`: 고객 조인과 날짜/시각 형식이 확인된 경우에만 true. 기본 false이므로 미확인 상태에서 환자 목록을 조회하지 않습니다.
- 의사명은 검증된 `Employe` 조인으로 조회합니다. 예전 `doctorNames` 설정은 더 이상 사용하지 않습니다. 의사명 연결이 누락된 행은 검증 모드에서 건수만 표시하며 실제 반영을 막습니다.

## 3. 데스크 PC 단독 검증 (반영·전송 없음)

한 번 실행할 때 한 번 조회하며 종료합니다. 작은 기간부터 확인하세요.

```powershell
node .\bogam-bridge\bridge.js --check 2026-11-28 2026-11-28
```

출력은 진료·예약 행 수, 미매핑 의사 행 수, 조회 전용 계정 검사 결과와 경과 ms뿐입니다. 환자 식별값과 진료 내용은 출력/저장/전송하지 않습니다. 결과가 없다는 이유로 보드를 비우지 않습니다. 날짜/환자/시간이 잘못됐거나 조인 중복이 충돌하면 검증 실패로 끝냅니다.

SQL 연결 제한 3초, 명령 제한 5초, PowerShell 프로세스 전체 제한 12초입니다. 타임아웃 시 명령 취소 및 연결 폐기, 필요시 프로세스 종료를 수행합니다. 진료보드→브리지 전송의 전체 제한은 16초입니다. SQL `SET`, `NOLOCK`, 스냅샷 설정 변경, 인덱스 생성 또는 재시도는 없습니다. 정상 READ COMMITTED 조회이므로 잠깐의 공유 잠금은 발생할 수 있으며 **동의보감 접수·수납 영향 여부는 데스크 PC 현장 검증 전에는 확정할 수 없습니다.** 기본 명령 제한은 이 때문에 짧게 잡았습니다.

동의보감에서 접수·예약·수납이 정상 동작하는지 담당자가 확인하면서 단독 조회를 실행해 시간/건수를 기록합니다. 평소보다 느려지거나 타임아웃이 생기면 조회 기간을 줄이고 중단하세요. 운영 DB 튜닝이나 설정 변경으로 해결하지 않습니다.

## 4. 원내망 연결 및 진료보드 서버 설정

1. 데스크의 외부 비밀 폴더에서 **`bridge-cert.pem`(공개 인증서)** 과 **`bridge-token.txt`(비밀)** 만 서버 PC의 접근 제한된 외부 폴더로 안전하게 복사합니다. PFX와 PFX 암호는 데스크 PC에서만 보관합니다. 같은 네트워크에 있다고 TLS를 생략하지 않습니다.
2. 데스크 브리지를 실행할 Windows 계정으로 시작합니다. 스크립트/정책 실행 차단이 있으면 기관의 기존 승인 절차를 따르며 SQL 또는 시스템 정책을 자동 변경하지 않습니다.

```powershell
$env:BOGAM_BRIDGE_CONFIG = "$env:LOCALAPPDATA\InhouseBogamBridge\bridge.json"
node C:\inhouse-bogam\bogam-bridge\bridge.js
```

3. 필요한 경우 Windows 방화벽의 **연동 HTTPS 포트만**, 진료보드 서버 IP만 허용합니다. 아래는 관리자가 검토 후 실행할 예시이며 설치 스크립트가 자동 실행하지 않습니다. SQL Server 포트(1433/동적 포트)와 Browser(1434)는 열지 마세요.

```powershell
New-NetFirewallRule -DisplayName 'Inhouse Bogam HTTPS bridge' -Direction Inbound -Action Allow -Protocol TCP -LocalAddress 192.168.0.20 -LocalPort 8788 -RemoteAddress 192.168.0.10 -Profile Private
```

4. 서버 PC에서 `server.config.example.json`을 **리포지토리 밖**으로 복사하여 URL, 토큰 파일, 인증서 경로를 수정합니다. `enabled: true`, **`applyEnabled: false`**를 유지합니다. 서버의 실제 실행 환경에 다음을 추가하고 기존 방식으로 재시작합니다. 서버 비밀 폴더 역시 해당 실행 계정만 접근하도록 설정하세요.

```powershell
$env:BOGAM_SYNC_CONFIG = 'C:\private-bogam-server\server.json'
# 이 환경변수를 설정한 세션에서 기존 진료보드 시작 스크립트 실행
```

기존 `CLINIC_REQUIRE_LOGIN`/세션 인증이 그대로 적용됩니다. 로그인 기능을 사용 중이면 새 API도 동일 세션이 필요합니다. 로그인 기능이 꺼져 있는 설치라면 기존 보드와 마찬가지로 로그인 보호가 없는 상태이며, 이 기능이 별도 사용자 인증을 도입하거나 기존 설정을 바꾸지는 않습니다. 새로고침 POST는 동일 출처 JSON 요청만 받습니다.

5. Desk를 새로고침해 **오늘 n/m명** 팝업 하단에서 기간을 고르고 **동의보감 새로고침**을 누릅니다. 검증 모드에서는 건수/시간/미매핑만 반환되며 환자 데이터는 전송되지 않습니다. 진행 중/검증 완료/연결 불가/시간 초과와 마지막 실제 반영 시각을 확인합니다. 마지막 반영은 검증만으로 갱신되지 않습니다. 상태 공유는 기존 SSE를 사용하고 자동 DB 재조회는 하지 않습니다.

Account는 진료번호+고객번호+날짜로 연결하며 최신 표본 80건 모두 1행이었습니다. **Account 후보가 0행 또는 여러 행이면 해당 진료번호의 기존 진료비총액(totalFee)을 유지**합니다. 나머지 세 금액은 고유 DigBill 행의 확인된 열에서 독립적으로 갱신하며 NULL은 기존 값을 유지합니다. 정확히 1행이면 NULL/공란은 해당 기존 값 유지, 실제 숫자 0은 기존 금액을 0으로 갱신합니다. `MAX`는 후보가 1행일 때 그 값만 취하기 위해 사용하며 다중 후보를 임의 선택하거나 합산하지 않습니다.

DigBill.db_DiagID와 Employe.emp_Code의 단일 열 고유 인덱스 확인 결과를 근거로 최대 1행 조인합니다. 금액에 할인·환불·미수·취소·분할수납에 대한 임의 합산/계산을 추가하지 않습니다. 원본 진료 레코드는 `bogamVisitRecords[JSON.stringify([진료번호,고객번호,날짜])]`에 저장합니다. 여러 진료번호를 하나로 합치지 않으며, 각 레코드에 각각의 금액을 보존합니다. 보드의 기존 날짜별 화면/통계 호환용 `visitHistory`에는 해당 날짜의 원본 진료번호가 하나일 때만 투영합니다. 다중 진료인 날짜는 기존 요약 값을 유지하고 완료 상태에 안내합니다. 이 요약은 여러 진료의 합계가 아니므로 별도 진료번호별 보고가 필요한 경우 해당 원본 레코드를 사용해야 합니다. 처리가 필요한 경우 기존 엑셀 대조 또는 별도 검증 후 규칙을 확장해야 합니다.

주상병 0/다중 행, 알 수 없는 보험/초재진 코드, 비어 있는 값으로 기존 값을 지우지 않습니다. 치료 목록·치료 메모·보드 수기 보정은 이 조회로 교체하지 않습니다. 주상병명은 아래 조건이 불충족이면 기존 값을 유지합니다. 금액 등 갱신 대상에 대한 보드 통계는 기존 필드와 진료 인덱스를 사용합니다. 원본 코드와 검증된 진료별 부가 정보도 기존 암호화 환자 JSON 안에 저장합니다.


### 주상병명 유효 이름 선택 규칙

사용자가 추가로 지정한 다음 규칙을 구현했습니다. 실제 데스크 DB에서 이 추가 쿼리의 값·실행시간을 재검증한 상태는 아닙니다.

1. 해당 진료번호의 `DigSick.ds_Base=1` 행이 정확히 1개여야 합니다. 그 행의 `ds_HCode`와 `ds_HNo`를 함께 사용합니다.
2. `MediHanSick.ms_Code = ds_HCode AND ms_No = ds_HNo`인 후보 중, `ms_DueDate`가 NULL/공란이거나 진료일 이하이고 `ms_ExpDate`가 NULL/공란이거나 진료일 이상인 행만 선택합니다. 경계일은 포함합니다. 날짜 변환에 실패하는 비어 있지 않은 값은 유효 후보로 간주하지 않습니다.
3. 공란 이름을 제외하고 앞뒤 공백을 제거한 이름의 서로 다른 값이 정확히 하나인 경우만 반영합니다. 동일한 이름의 중복 행은 COUNT(DISTINCT)로 한 번만 셉니다. 이름 비교는 쿼리 표현식의 이진 collation으로 수행하며 DB/SQL Server 설정을 변경하지 않습니다.
4. 주상병 행이 0개/여러 개이거나 유효 이름이 없거나 서로 다른 유효 이름이 여러 개이면 기존 주상병명을 유지합니다. MAX로 임의 이름을 선택하지 않습니다. MAX 결과는 유일성이 확인된 경우에만 사용합니다.
5. 주상병명은 진료번호별 원본 레코드의 `chiefComplaint`에 저장합니다. 그 날짜의 원본 진료가 하나일 때만 `visitHistory[날짜].chiefComplaint`에도 투영합니다. 환자 마스터의 `chiefComplaint`는 가장 최근 방문인 경우만 갱신하여 과거 자료로 현재 상병명을 덮어쓰지 않습니다. `memo2` 등 치료 메모는 변경하지 않습니다.

모든 후보 확인은 기존 버튼 1회 조회의 SELECT 배치에 포함되며 정기 조회·추가 DB 접속·재시도를 만들지 않습니다. 기존 짧은 제한 시간, 읽기 전용 계정 검사, 전체 반영 트랜잭션은 유지합니다.


### 최신 80건 검증에 따른 보험 상세명과 예약 정책

- (da_Insure, da_InsuKind) = (1,0): 건강보험, (1,3): 차상2종, (2,1): 급여1종, (2,2): 급여2종.
- `dm_NoneInsu=0`인 확인 조합만 위 일반 상세명을 생성합니다. `dm_NoneInsu=1`이고 (1,0)인 확인 사례만 `비*건강보험`을 생성합니다. 다른 조합의 비* 접두사나 NoneInsu가 불명확한 경우는 추정하지 않습니다. 원본 상태도 `bogamNoneInsurance`로 보관합니다.
- 자동차보험은 확인된 상세 코드 17~19만 지원합니다. `da_InsuKind = InsuComp.inc_Code` 후보를 집계하여 각 열의 서로 다른 값이 하나이고, 오른쪽 공백 제거 후 `inc_Name`과 `inc_Caption`이 정확히 같으며 비어 있지 않을 때만 `자보:` + 이름을 저장합니다. 표본 5건에서 일치했습니다. 두 열의 이름이 다르거나 후보가 모호하면 우선순위를 추정하지 않고 기존 표시명을 유지합니다. 보험사 조인으로 진료 행이 증식하지 않도록 APPLY 집계를 사용합니다.
- 금액은 수납액으로 대체하거나 예외 합산하지 않습니다. 두 날짜에서 동일 고객/날짜의 양수 진료번호 다중 사례 및 할인·환불·미수 검사값 사례가 없었으므로, 예외 계산 규칙이 검증된 것으로 간주하지 않습니다.
- DigBook에서 확인된 고유 인덱스는 `(dbk_CustID,dbk_DiagDate)`입니다. `dbk_BookID` 단독 유일성·변경 유지와 `dbk_Accept` 의미는 미확인입니다. Accept=0/1의 의미를 추정하거나 날짜가 바뀐 예약을 ID로 자동 연결하지 않습니다. 다만 후속 사용자 요청에 따라, 현재는 엑셀과 같이 결과에 포함된 날짜의 명단을 교체하므로 그 날짜의 누락된 기존 예약은 제외됩니다. 결과에서 날짜 자체가 빠지면 유지합니다. ID 기반 연결·상태 판정의 확장은 실제 전후 SELECT 검증 후에만 진행합니다.

이전에 dm_DiagType에서 저장했던 `bogamVisitTypeCode`가 있다면 과거 메타데이터일 뿐 새 분류 기준으로 사용하지 않습니다. 올바른 dm_DiagMode 조회가 반영되면 확인된 분류와 새 원본 코드가 갱신됩니다. 이번 변경은 개발 PC에서 가상 데이터로 검증하며 운영 DB에는 접속하거나 설정·권한을 변경하지 않습니다.


### 엑셀 방식으로 맞춘 후속 변경

- 예약 저장은 수동 엑셀과 동일한 날짜별 전체 교체 함수를 사용합니다. 11월 28일의 예약이 한 건이라도 반환되면 28일 전체 명단을 그 결과로 교체합니다. 28일의 결과가 0건이면 날짜 자체가 반환되지 않으므로 기존 명단을 자동 삭제하지 않습니다. 이는 빈 날짜를 명시해야 하는 수동 엑셀과 동일합니다.
- 접수 시각은 원본의 초까지 보존합니다. 예: 09:30:01 → 한국시간 09:30:01. 초가 없는 입력은 :00으로 저장합니다. 예약 시각은 기존 엑셀 예약 슬롯과 같은 분 단위입니다.
- 계정 권한·시간 제한·동시 조회 단일화·실패 전체 롤백·치료 메모 보존은 유지합니다. 미확인 코드와 상병/금액 후보의 모호성을 임의로 해석하지 않습니다. 따라서 입력값 검증, 이름 충돌 환자만 저장 보류, 최신 방문에만 기본 연령 갱신 등 보수적 DB 연동 처리는 엑셀과 차이가 남아 있습니다.


### 진료·접수 이름 충돌 처리

수동 진료·접수 엑셀과 같은 기준으로 차트번호별 입력 이름을 먼저 확인합니다. 입력에 서로 다른 이름이 둘 이상이면 해당 차트번호 전체를 제외합니다. 기존 보드에 해당 차트번호가 있는데 입력 이름과 일치하는 환자가 없으면 역시 해당 차트번호를 제외합니다. 기존에 같은 차트번호의 여러 환자가 있어도 입력 이름과 정확히 일치하는 환자가 있으면 그 환자만 갱신합니다.

충돌하지 않은 진료와 별도의 예약 명단 처리는 계속 진행합니다. 예약은 기존 예약 엑셀처럼 날짜별 전체 교체하며, 진료·접수 환자 저장 보류를 예약 취소로 해석하지 않습니다. 충돌한 진료 환자의 기존 진료 기록·메모는 변경하지 않습니다. 모두 충돌하면 진료 저장 0건과 보류 건수를 표시합니다. 이름 충돌을 제외한 잘못된 원본/조회·전송·저장 실패는 여전히 전체 롤백합니다.
